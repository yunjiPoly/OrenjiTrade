## 3. How a scan works

### 3.1 The owner's plan, validated

Kept:
- The card is found from two things printed on it, its name and its set code, matched against our catalog.
- The two areas of the card to read, from the owner's coordinates (3.3).
- One reader interface, OcrProvider, so readers can be swapped.
- The normalisation, with look-alike characters swapped only when the catalog confirms the result.
- Never the 8-digit passcode.
- The set name comes from the catalog through the code. The rarity is the collector's pick when a code comes in several.
- An image matcher (DINOv2) as a later fallback behind an interface. It is not built now (ML hold).

Changed:
- The text is read on the phone, not by PaddleOCR in Python.
  - The app can't run Python. A server would mean uploading every photo, paying for a machine and waiting on the network for each scan.
  - The phones' own readers are free, offline and good at printed text: Apple Vision on iPhone, Google ML Kit on Android. The photo never leaves the phone.
- No card detection, perspective correction or preprocessing chain (CLAHE, Otsu, adaptive thresholds) for now.
  - The card-shaped frame on the camera does the aligning, and these readers do best on the plain photo.
  - Add them only if the real-card check (section 7) shows they're needed. On iPhone, Vision's built-in rectangle detection is the first thing to try.

Added:
- The name and the code check each other in the catalog (3.5).
- Pendulum cards print the code in another place, so they get a second spot (3.3).

### 3.2 Taking photos

- Camera: expo-camera's CameraView, one still photo per tap. No live frame processing, no EXIF.
- The shutter never waits: each photo gets a "Reading…" tile and is read in turn while the collector keeps shooting.
- The frame on screen has the card's shape (59 × 86 mm). The preview fills the screen, so it shows only part of the photo. Map the frame to photo pixels with the same cover scaling, and test it with a card touching each edge of the frame.
- Library: expo-image-picker, several photos at once (up to 50), with LIBRARY_PHOTO_OPTIONS, one card per photo.
- Every photo file the scan made or copied is deleted when the scan ends (cards added, or the scan left).

### 3.3 Reading on the phone

- One interface in src/features/scan: the owner's OcrProvider, in TypeScript.
  - recognizeName(photo, box) and recognizeSetCode(photo, box) return an OcrResult: the text, a confidence (null when the engine gives none), and the raw lines.
  - recognizeLines(photo) reads the whole photo and returns lines with their boxes.
  - One implementation on the device and a fake for tests. No cloud reader: no accounts, no uploads.
- The engines:
  - iOS: Apple Vision (VNRecognizeTextRequest at the accurate level, language correction off for the set code);
  - Android: ML Kit text recognition, with the bundled model so it works offline from the first scan.
- Default: a small local Expo module in apps/mobile/modules (npx create-expo-module --local). Both engines are built in or free, the module returns lines with boxes and confidences, and no third-party JavaScript package comes in.
- A maintained library is fine instead, but only if it:
  - supports Expo SDK 57 and React Native 0.86 with the New Architecture;
  - reads a still image offline and returns line boxes;
  - has a compatible licence;
  - is pinned.
  Say which you chose and why.
- Camera photos: crop each area from the photo with about 10 % margin, and read the code area at twice its size (the code is tiny). As fractions of the card:
  - Name: x 4–86 %, y 2–11 % (the owner's 15–360 × 10–65 on a 421 × 614 card).
  - Set code: x 69–96 %, y 71–76 % (the owner's 290–405 × 435–465).
  - When the set code area holds no code, read the Pendulum spot: Pendulum cards print the code at the left, under the pendulum text. Start with x 4–45 %, y 70–80 %. No other card type gets a second spot (the owner's call).
  - Keep these numbers in one config file and correct them from the real-card check.
- Library photos, or areas that gave nothing: read the whole photo and pick the lines by shape and position (3.4). If that finds nothing, try the photo turned 90°, 180° and 270° (library photos only).

### 3.4 Picking the text (pure TypeScript, unit-tested)

- Code candidates, at most 3, best first. A printing code is:
  - a set part of 2 to 5 letters or digits (LOB, SDK, RA01, MP22, L5DD);
  - a dash;
  - an optional region: EN, or E on old English prints from Europe (old North American prints have none, like LOB-005). Capture other regions too (FR, DE, IT, SP, PT, and old F, G, I, S, P), so the server can refuse them (3.5);
  - 2 or 3 digits, sometimes after one letter (LAVD-ENS08).
- Clean each candidate:
  - uppercase it and remove the spaces;
  - read –, —, _, . and ~ between the parts as "-";
  - keep only A–Z, 0–9 and "-".
  Don't swap letters and digits here: the server does that against the catalog.
- What to skip:
  - the 8-digit passcode at the bottom left (never use it);
  - ATK/ and DEF/ lines and LINK-n;
  - "1st Edition" and "LIMITED EDITION".
- Name candidates, at most 3: the Name area's text. On a whole-photo read, take the highest lines with at least 3 letters that aren't:
  - a code;
  - a [SPELL CARD] or [TRAP CARD] line;
  - an attribute word (DARK, LIGHT, EARTH, WATER, FIRE, WIND, DIVINE);
  - level stars or stats.
- The phone sends its candidates to the API (3.5). It never decides alone.

### 3.5 Matching on the server: POST /api/v1/cards/scan-match

The body has the game ("yugioh"; anything else is a 400), codes (0 to 3) and names (0 to 3), best first.

The rules are deterministic and unit-tested, and run in a few grouped queries. Reuse printingRefsByCodes, printingRefsOfCards and the name search behind /cards/suggest.

1. Exact codes. Look up:
   - each code as read;
   - the other form of an old code (LOB-005 ↔ LOB-EN005; LOB-E001 → LOB-EN001);
   - a missing dash, tried at each place it could go.
2. Look-alike characters, only when the catalog confirms.
   - Variants swap O↔0, D↔0, I↔1, L↔1, S↔5, B↔8, Z↔2 and G↔6.
   - Letters become digits in the number part, digits become letters in the region, and both ways in the set part.
   - At most 64 variants, looked up in one query. A variant counts only when the catalog has it.
3. The name: the cards whose name is close to what was read. Exact after CatalogText.normalise first, then prefix, then trigram, as /cards/suggest does.
4. Deciding:
   - The code's card has the read name, or no name was read: that card. "Close names" starts around pg_trgm similarity 0.5; tune it in section 7.
   - With no name, a look-alike variant counts only when it is the only one the catalog has.
   - The name clearly points to another card: the name wins. Take that card's printing whose code is one look-alike character from the read one, when exactly one is; otherwise its printing is unknown. The code's own card goes to otherMatches.
   - Several candidates and nothing to choose between them: not found, and the candidates go to otherMatches.
5. English cards only (the owner: "DONT detect french cards"). When a code carries another language's region (MACR-FR036), the answer is NOT_FOUND, whatever the name says. Never match such a card through its English code or as a look-alike.
6. Status:
   - FOUND: one card and one printing (the code exists in one rarity, or the card has a single printing);
   - PICK_RARITY: one card and one code that comes in several rarities;
   - PICK_PRINTING: the card is known but not the printing (the code was unreadable or matched none of its printings);
   - NOT_FOUND: nothing.
7. The response:
   - status;
   - the card (id, name, picture);
   - the printing when found (id, code, set name, rarity);
   - rarities, for PICK_RARITY (printing id and rarity);
   - printings: every printing of the card, newest set first, with set name and rarity (the Pick printing list);
   - otherMatches, at most 6: codes one look-alike character away that belong to other cards, and other cards with close names. Here 3/8, 6/8, 5/6, 0/8 and 1/7 count as look-alikes too; they are shown, never accepted on their own;
   - what was read.

More rules for this endpoint:
- Pictures only through /api/v1/public/card-images (ADR 0015), never a provider address.
- Signed-in collectors only. It checks the flag: 404 FEATURE_DISABLED when off.
- It is a POST, so the read text stays out of addresses and access logs. Never log the read text with a user id.
- One photo per call. The default limit of 120 requests a minute per collector is plenty.
- Put the matcher behind one interface: text now, an image matcher later.

### 3.6 Adding: POST /api/v1/inventory/items/batch

- The body:
  - visibility: PRIVATE by default, or PUBLIC;
  - binderId: optional, one of the caller's binders, else 404;
  - lines, 1 to 500: printingId and quantity. Lines of the same printing are summed.
- One transaction. Every line gets the same defaults as a card added on the phone: R2's choices (availability TRADE_OR_SALE, accepts offers off, condition not stated). Until R2 is merged, use today's defaults, then align after merging.
- A line adds its copies to the collector's equal item when there is one; otherwise it creates one. Equal means the same printing, language, condition, edition and finish, and the same visibility and binder.
- Reuse importLines' rules:
  - the owner lock first, then its lock order;
  - the reconciliation (ListingReconciler), so a public card publishes InventoryItemPublished and wishlist alerts and the Home feed see it;
  - inventory.items.max checked for the whole batch: 429 LIMIT_REACHED, with nothing written.
- The items count as confirmed (freshness).
- It answers how many items were created and how many got extra copies, with their ids.
- Use new controller and service classes, so R2's files barely change.
