# Owner account security checklist

OrenjiTrade is run by a solo owner. Losing one of the accounts below means losing the product,
the users' data or the domain, so each of them needs a second factor and a recovery plan.
Check the list before the first real users and then every quarter; record the date of each
review at the bottom. Drafted by engineering; the accounts marked `[to confirm]` may not exist yet.

## 1. Accounts and second factors

| --- | --- | --- | --- |

Rules that apply to every row: unique passwords generated by the password manager; recovery
e-mail and phone reviewed quarterly; sign out of unused sessions; no credential in chat, tickets,
`.env` files that are committed, CI logs or screenshots (`docs/security/README.md` section 4).

## 2. Admin MFA in the API — actual values per Spring profile

`orenji.security.admin.require-mfa` (binding: `OrenjiSecurityProperties.Admin.requireMfa`,
default `true`; enforcement: `AdminAuthorizationManager` on `/api/v1/admin/**` and on the
moderator patterns) as declared in `apps/api/src/main/resources/application.yml` on 2026-10-05.
There is a single configuration file; the profile documents only override what they list.

| Profile | `require-mfa` | Where it comes from |
| --- | --- | --- |
| base document (every profile inherits it) | `true` | `orenji.security.admin.require-mfa: true` (line ≈ 158) |
| `local` | **`false`** | the `on-profile: local` document (line ≈ 404); the Auth emulator has no second factor |
| `test` (JUnit / Testcontainers) | **`false`** | the `on-profile: test` document (line ≈ 504); `AdminMfaIT` switches it back to `true` with `@TestPropertySource` to prove the refusal |
| `dev` | `true` | inherited: the `on-profile: dev` document does not override it |
| `staging` | `true` | inherited: no override |
| `prod` | `true` | inherited: no override |
| no profile at all | **`false`** | `spring.profiles.default: local` makes a JVM started without a profile run as `local` |

What the check does today: the Firebase ID token must carry a non-blank
`firebase.sign_in_second_factor` claim (`FirebaseIdentityTokenVerifier` → `secondFactorUsed`);
otherwise the admin route answers `403` with the `MFA_REQUIRED` reason. **There is no check of
how recent the second factor is** (`auth_time` is parsed but not compared); `docs/security/
README.md` section 7 was corrected on 2026-10-05 to say so. A freshness window (for example
12 hours) is a hardening follow-up.

Finding to fix before any cloud deployment (out of scope of the launch task, reported in
`IMPLEMENTATION_STATUS.md`): Terraform sets `SPRING_PROFILES_ACTIVE` to `development` /
`staging` / `production` (`infrastructure/terraform/environments/*/main.tf`, and the matrix in
`docs/deployment/environments.md`), while `application.yml` declares the profile documents
`dev` / `staging` / `prod`. In cloud **dev** and **prod** no profile document matches, so only
the base document applies: `require-mfa` is still `true` (good), but the `prod` document's
overrides would not apply (Hikari pool size from `DATABASE_POOL_SIZE`, the empty default of
`SERVICE_TOKEN` instead of the base `local-service-token`, ECS structured logging) and the
`@Profile({"staging", "prod"})` `ServiceTokenStartupValidator`, which refuses the local default
service token, would **not** run in production. Terraform does inject `SERVICE_TOKEN` from
Secret Manager, so the exposure is the missing safety net, not an open door. Align the names
(Terraform or `application.yml`) before the first deploy.
